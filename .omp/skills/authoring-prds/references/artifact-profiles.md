# Product Document Profiles

## One-pager

Use for a bounded decision or early alignment. Include problem, user, evidence, appetite, solution shape, alternatives, risks, success/kill signal, and requested decision. Do not add implementation requirements unless they decide the bet.

## Full PRD

Use for cross-functional implementation when product behavior, scope, data, rollout, and acceptance need one durable contract. Use stable requirement IDs.

## Feature brief

Use when a mature product and platform already supply most context. Include delta from current behavior, affected users/flows, requirements, instrumentation, rollout, and compatibility.

## User-story package

Use when the destination requires issue-shaped stories. Preserve one parent outcome, story IDs, acceptance, dependencies, edge states, and PRD references. Avoid persona theater.

## Technical specification

Use after product behavior is stable enough to design implementation. Include architecture, interfaces, data model, failure modes, security, performance, migration, observability, test plan, and rollback. Link requirements rather than rewriting them.

## GTM brief

Use when launch positioning and distribution require alignment. Include ICP, problem, promise, proof, objections, offer, channels, launch stages, claims/evidence policy, conversion events, and feedback loop. It does not replace the product PRD.

## Selection rule

Choose the smallest profile that makes the next decision or execution unambiguous. More sections are not more rigor when nobody needs them.
